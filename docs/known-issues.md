# 既知の注意点・実装上の落とし穴

## LiveKit: 選択的購読(updateSubscriptions)の早すぎるタイミングでの失敗

**発見日**: 2026-08-20(target-pro負荷検証 Test16の副産物、
`deploy/livekit/LOAD_TEST_PLAN.md`参照)

### 問題の内容

Publisherがトラックを公開した直後に、LiveKit Server APIの
`RoomServiceClient.updateSubscriptions(room, identity, trackSids, true)`
で特定のトラックへの購読を要求すると、**サーバー側でそのトラックが
まだ完全に認識されておらず、購読が失敗する**ことがある。

検証では、トラック公開の約15秒後に購読要求を行ったところ、30件中
15件が失敗した(サーバーログに`unsubscribing from track after
notFoundTimeout`・`error: "track cannot be found"`として記録される)。
**このとき`updateSubscriptions`のAPI呼び出し自体は成功レスポンスを
返す**ため、呼び出し側のエラーハンドリングでは検知できない、
サイレント障害になる。

同じ処理を、トラック公開から30秒待ってから実行したところ、全件
成功した。

### Globy本体への影響(想定されるリスク)

Globyで「相手を選んで1:1画面共有・ビデオ通話を見る」ような、
クライアントまたはサーバーAPI経由での選択的購読を実装する場合、
**相手が配信を開始した直後にユーザーが選択・購読しようとすると、
同様の理由で「相手を選んだのに映像が表示されない」という、原因
不明のバグとしてユーザーに現れる可能性がある**。

### 推奨される対策

- トラック公開から一定時間(検証結果を踏まえ、安全マージンを取って
  数十秒程度)待ってから購読を許可する
- 購読リクエスト後、実際にトラックが届いているかをクライアント側で
  確認し、一定時間届かなければリトライする仕組みを入れる
- サーバー側のログ(またはLiveKit Webhook: `track_published`
  イベント等)で購読失敗を検知できる仕組みを用意し、サイレント障害を
  防ぐ

### 検証時の技術メモ(参考)

`lk room join --publish`は、指定した動画ファイルの再生が終わると
自動ループせず配信を停止する(プロセス自体は生存する)。長時間の
配信テストを行う際は、ファイル長がテスト時間を上回るようにするか、
別途ループ再生の仕組みを用意すること(target-pro自体の問題ではない、
テストツール側の制約)。
