# lk load-test 実測プラン

## 実測結果(2026-08-17、接続タイミングのランダム化検証)

### 1. 従来のテストスクリプトの接続タイミングの実態

`lk load-test`(公式CLI)の接続タイミングを確認したところ、以下のように
機械的・規則的であることを確認した:

- **接続開始**: `--num-per-second`(例: 2)による一定間隔のバッチ処理。
  ランダム性はなく、メトロノーム的に一定間隔で新規接続が発生する
- **ICE gathering〜Track subscription**: ツール内部の処理で、実際の
  ネットワーク遅延による自然なばらつきは生じるが、意図的なジッターは
  注入されない(トリガーされた瞬間に即座に処理を開始する)
- **切断**: `--duration`で指定した秒数が来ると、全クライアントがほぼ
  同時に切断する

### 2. ランダム化テストの実施方法

`lk load-test`自体にはクライアントごとのジッター注入機能が無いため、
**50個の独立した`lk load-test`プロセス(各1人分:publisher1+subscriber1)を、
それぞれ独立したランダム遅延で起動する**方式で近似した:

- 接続開始: 0〜25秒の範囲でランダム(機械的バッチ(約25秒で到達)と
  総所要時間を揃えて比較しやすくした)
- 保持時間: 60〜90秒のランダム(退室タイミングも自然に分散)
- 生成元VPS(157.120.59.134)から本番grovina-livekit-prodへ、同一ルームに
  50プロセスを同時起動するシェルスクリプトで実施

### 3. 結果比較

| 指標 | 機械的バッチ(条件D、`--num-per-second 2`) | ランダム化(今回、独立50プロセス) |
| --- | --- | --- |
| 接続完全失敗 | 26/50(52%) | 21/50(42%) |
| 接続できた分のパケットロス(平均) | 9.1% | 約14.2% |
| prod CPU(ピーク) | 43.5% | 約40% |
| prod CPU(終了後) | 1.13%(正常復帰) | 0.56%(正常復帰) |
| 完全ブロック(生成元→prod遮断) | 発生せず | 発生せず |

### 4. 考察

**「機械的な一斉接続が問題を過大に発生させている」という仮説は、明確には
支持されなかった。** 接続完全失敗率はランダム化によりやや改善した
(52%→42%)が、実際に接続できた利用者のパケットロスはむしろ悪化した
(9.1%→14.2%)。総合的には**同程度〜やや悪い結果**であり、ランダム化に
よる明確な改善は確認できなかった。

一方、既存の条件Dの段階的ランプ実測(90秒間隔で5人ずつ、数分〜十数分
かけて投入)では、閾値が明確に改善していた(30〜35人→40〜45人)。この
2つの結果を合わせると、**接続タイミングが「規則的か/ランダムか」という
"質"よりも、「全体としてどれだけ短い時間窓に新規接続が集中しているか」
という"密度・総所要時間"のほうが支配的な要因である**可能性が高い。
今回のランダム化(0〜25秒の窓)は、機械的バッチ(約25秒で到達)と
ほぼ同じ密度だったため、同程度の結果になったと解釈するのが自然である。

**実運用への示唆**: 「利用者は自然にバラバラのタイミングで入室するので
実際には大丈夫なはず」という楽観的な想定は、この検証結果からは支持
されない。**閾値の目安(30〜35人=急激な同時接続、40〜45人=数分かけて
分散)は、入室が規則的か自然かに関わらず、「短時間にどれだけの人数が
集中するか」を基準に据えるのが妥当**と考えられる。

## 実測結果(2026-08-16、パターンD: LiveKit単体への直接接続、A〜D総合考察)

パターンA・B・Cがいずれも遮断を引き起こさなかったことを受け、最後に残る
「D: LiveKitサーバーへの直接接続のみ(Supabase認証・Realtimeなし)」を、
A・B・Cと同一の記録体裁で単発クリーンに実施した(過去の条件C・Dランプ実測も
実質的にD相当だが、A・B・Cと直接比較できる形で結果を残すため改めて実施)。

### 実施条件
生成元VPS(157.120.59.134)から`lk load-test`で、本番grovina-livekit-prodへ
50人(pub+sub)、低画質、`--num-per-second 2`、60秒保持。実施前にprodへの
到達性(前回A・B・C実施からの残存遮断がないこと)を確認済み。

### 結果

| 項目 | 結果 |
| --- | --- |
| Subscriber接続失敗 | 26/50(52%)が`could not connect: context deadline exceeded` |
| パケットロス(接続できた分) | 9.131% |
| エラー件数 | 26件 |
| prod CPU(接続確立直後ピーク) | 43.5% |
| prod CPU(テスト終了後) | 1.13%(正常に復帰、再起動不要) |
| 生成元→prod到達性(実施前後とも) | 443番到達可(**今回は完全ブロックには至らなかった**) |

→ **今回は完全な通信遮断(前回35人時のような443/22番の全面遮断)までは
発生しなかったが、52%のsubscriber接続が失敗し、パケットロスも9.1%と
閾値(10%)寸前まで悪化する、深刻な劣化が発生した。** 完全ブロックの
発生有無には実行ごとのばらつきがあるとみられるが(閾値付近の人数では
毎回同じ結果になるとは限らない)、50人規模でLiveKit単体の接続確立に
明確な支障が出ること自体は、既存の条件C・D実測(35人で完全ブロック)と
一貫している。

### A〜D総合考察

| パターン | 50人規模での結果 |
| --- | --- |
| A(Web閲覧) | 遮断・劣化なし |
| B(Supabase認証) | 遮断・劣化なし(Supabase自身のレート制限のみ) |
| C(Supabase Realtime) | 遮断・劣化なし |
| D(LiveKit単体) | **深刻な劣化(接続失敗52%・パケットロス9.1%)、実行によっては完全ブロックも発生(条件C・D実測で35人時に確認済み)** |

4パターンを通じて、**遮断・劣化が発生したのはLiveKit接続(D)のみ**という結果になった。これにより、WebARENA Indigo側の異常検知は「単一送信元IPからの大量の同時アウトバウンド接続」という一般的な特性に対してではなく、**LiveKit接続確立時のWebRTC/UDP通信(STUN/TURNネゴシエーション、メディアトラフィック)に固有の通信パターンに反応している可能性が高い**、という結論を最終的なものとする。実運用への示唆は既存の記載(30〜35人=急激な同時接続、40〜45人=分散接続の目安)から変更なし。

## 実測結果(2026-08-16、パターンA・B・C: WebARENA Indigo遮断のトリガーレイヤー切り分け)

これまでの負荷テスト(条件C・D、10〜30人ランプ)は、いずれも`lk load-test`による
単一送信元VPSから本番LiveKitサーバー(grovina-livekit-prod)への直接接続、
すなわち「D: LiveKit単体」パターンに実質的に相当していた。この実測により
「WebARENA Indigo側ネットワーク機器が、単一送信元からの新規接続集中を検知して
自動遮断する」現象自体は確認済みだったが、**遮断の引き金がLiveKit接続(WebRTC/
UDP/TURN)固有の特性によるものか、それとも単に「同一送信元IPからの大量の
同時アウトバウンド接続」自体がトリガーなのか**は未切り分けだった。

これを切り分けるため、Web閲覧(A)・Supabase認証(B)・Supabase Realtime
WebSocket(C)の3パターンで、同じ生成元VPS(157.120.59.134)から50人相当の
同時接続を発生させ、遮断の有無を確認した。

### 実施しなかったパターンについて

- **D(LiveKitサーバーへの直接接続)**: 上記の通り、既存の`lk load-test`実測
  (条件C・D、10〜30人ランプ)がこのパターンに相当する大量のデータを既に
  保有しているため、本ラウンドでは再実施しなかった。
- **E(実際のフルフロー、Googleログイン込み)**: 50人分のGoogleアカウントを
  用意し自動ログインさせることが技術的に困難(reCAPTCHA・2段階認証等の
  自動化阻害要因)なため、断念した。B(Supabase認証エンドポイントへの
  同時アクセス)で、認証まわりの通信集中という要素を可能な範囲で代替した。

### パターンA: Web閲覧のみ(本番サイトのトップページへ50件同時アクセス)

生成元VPS(157.120.59.134)から本番サイト`https://avatar-pi-dun.vercel.app/`
(公開・ログイン不要のトップページ)へ、50件のcurlをバックグラウンド起動し
ほぼ同時に発行(`wait`で完了待ち)。

| 項目 | 結果 |
| --- | --- |
| 応答コード内訳 | 200 × 50/50(全件成功) |
| 応答時間 | min 1.02s / median 1.29s / avg 1.26s / max 1.44s |
| 全50件の実発行〜完了までの壁時計時間 | 約1.53秒 |
| 生成元→prod到達性(実施前) | 443番・22番とも到達可 |
| 生成元→prod到達性(実施後) | 443番・22番とも到達可(変化なし) |

→ **遮断は発生しなかった。** Vercel側のレスポンスも全件正常。

### パターンB: Supabase認証エンドポイントへの同時アクセス(50人分)

実際のGoogleログインは自動化できないため、Supabase Auth API
(`<SUPABASE_URL>/auth/v1/token?grant_type=password`)へ、ダミーのメール
アドレス・パスワードで50件のPOSTリクエストをほぼ同時に発行して代替した

→ **遮断は発生しなかった。** 20件が429(Supabase自身のレート制限)を
返した点は、WebARENA Indigo側の遮断とは無関係な、Supabase側の想定内の
挙動(短時間の同一操作の連打に対する保護)である。接続自体は全件正常に
確立・応答しており、生成元VPSのアウトバウンド接続が妨げられた形跡はない。

| 全50接続の実発行〜完了までの壁時計時間 | 約6.0秒 |

→ **遮断は発生しなかった。** 50本のWebSocket接続・チャンネル購読は全件
クリーンに成立した。

### 考察: 遮断のトリガーレイヤーについて

1. **A・B・Cのいずれも遮断を引き起こさなかった。** 事前の予想
   (「A・B・CはいずれもVercel・Supabaseという別会社のインフラにしか
   アクセスしないため、理論上WebARENA Indigo側の遮断機構が働く余地は
   なく、遮断は起きない可能性が高い」)通りの結果となった。
2. **これにより、遮断のトリガーは「単一送信元IPからの大量の同時
   アウトバウンド接続」という一般的な特性ではなく、既存実測(D相当)で
   確認されている**LiveKit接続(WebRTC/UDP、STUN/TURN経由の
   メディア確立を伴う接続)固有の通信パターン**に強く紐づいている
   可能性が高いと考えられる。**具体的には以下のいずれか(または
   組み合わせ)が疑われる:
   - UDPベースのメディアトラフィック(WebRTC)の急増を、TCPベースの
     HTTP/WebSocket(A・B・C)とは異なる異常検知ロジックで扱っている
   - 同一ルームに対する大量の新規ICE/STUN/TURNネゴシエーションが
     短時間に集中すること自体が、ポートスキャンやDDoS的挙動と誤検知
     されやすい
   - 単純に転送量(bps)の絶対値が、A・B・C(軽量なHTTP応答・
     WebSocketハンドシェイクのみ)よりLiveKit映像/音声トラフィックの
     方が桁違いに大きいため、帯域ベースの閾値に先に抵触している
3. **実運用への示唆**: Web閲覧・ログイン・Realtimeプレゼンス機能自体は、
   50人規模の同時アクセスがあってもWebARENA Indigo側の遮断リスクは
   低いと考えてよい。引き続き懸念すべきはLiveKitのメディア接続
   (音声・ビデオ・画面共有)の同時確立数であり、この点は既存のD実測
   (条件C・D)で得られた「30〜35人(急激な同時接続)/40〜45人
   (分散接続)」という閾値の目安を踏襲する。

一時VPS(生成元、157.120.59.134、WebARENA Indigo Tokyo)から本番grovina-livekit-prodへ`lk load-test`を実施。前回(10〜30人ランプ)で判明した「WebARENA Indigo側ネットワークが単一送信元からの新規接続集中を検知して自動遮断する」現象について、より詳細な閾値特定(条件C)と、接続ペースが遮断に与える影響(条件D)を検証した。

### 条件C: 単一送信元・通常ペース(`--num-per-second 2`)での段階的閾値特定

各段階は単発のクリーンな実行(前段階のCPUがベースラインへ戻ったことを確認してから開始)。

| 人数(pub+sub) | 結果 |
| --- | --- |
| 15 | パケットロス0%、エラー0(完全にクリーン) |
| 20 | 接続失敗なし、パケットロス7.5%(軽微な劣化) |
| 25 | 接続失敗5/25(20%)、パケットロス1.23% |
| 30 | 接続失敗少数、パケットロス0.67% |
| **35** | **生成元→prod間が443番・22番とも完全に到達不能(ブロック発生)**。prod自体はCPU正常・再起動不要 |

→ **通常ペースでの閾値は30〜35人の間**。

### 条件D: 5人ずつのバッチを約90秒間隔で投入し、接続をゆっくり分散させた場合

「遮断の基準は人数の絶対数ではなく、短時間の新規接続の集中度(勢い)ではないか」という仮説を検証。同一ルームへ、5人(pub+sub)のバッチを90秒間隔で継続投入し、各バッチ投入直前に生成元→prod間の到達性を自動チェックして、遮断を検知したら以降のバッチ投入を自動停止するスクリプトで実施。

| 累計人数 | 到達までの時間 | 結果 |
| --- | --- | --- |
| 30 | 約7.5分 | 問題なし(CPU 28.8%) |
| **35** | 約9分 | **問題なし**(CPU 32〜36%)。条件Cでは同人数でブロックが発生していた |
| **40** | 約10.5分 | **問題なし**(CPU 6〜18%台で推移)。ただし直近5人分のバッチ(36〜40人目)自体はパケットロス12.7%・エラー4件と劣化の兆候あり |
| 45(目標) | 約12分 | **ブロック発生**。バッチ投入直前の到達性チェックで検知し、スクリプトが自動的に以降のバッチ投入を中止。prod自体は健全(CPU 2.6%、再起動不要)。ブロック後も既存の40人分の接続にエラー・切断は見られず、新規接続のみが遮断された模様 |

→ **ゆっくり接続させることで閾値を30〜35人から40〜45人へ押し上げられた**が、無制限に回避できるわけではなく、累計接続数自体にも上限があるとみられる。

### 結論

1. **「接続の勢い(短時間の集中度)」は遮断の一因として支持された。** 同じ人数でも、接続を時間的に分散させることで許容できる人数が明確に増加した(閾値が約10〜15人分、実質的に3〜4割程度改善)。
2. **ただし「勢い」だけが全てではない。** ゆっくり接続させても、累計40〜45人のどこかで結局遮断が発生しており、単一送信元IPからの累計接続数自体にも上限がある可能性が高い。
3. **実運用への示唆(1つの会社・教室などの単一共有回線からの同時入室)**:
   - 全員がほぼ同時(数十秒以内)に入室する最悪ケースでは、**30人程度が安全ライン**、35人以上は遮断リスクが高い
   - 入室が自然に数分かけて分散する場合(現実的な利用シーンに近い)は、**40人程度までは概ね安全**とみられるが、40人に近づくと劣化の兆候が出始めるため、余裕を持たせるなら**30〜35人程度を目安**とするのが無難
   - いずれにせよ、**単一の共有回線からの同時利用は50人規模になると高い確率で問題が発生する**ため、大人数の教室・オフィスでの利用を想定する場合は、この点を利用者への案内(ヘルプページ等)に含めることを推奨する

## 検討: 負荷生成元をスマホテザリングに変更する案(2026-08-16、判断のみ・未実施)

10〜30人ランプ実測(下記)で20〜30人からパケットロスが増加した件について、
別クラウドVPSを新規契約せずコストをかけずに対応できないか、負荷生成元を
スマホテザリング(4G/5G)に切り替える案の妥当性を検討した。**判断のみ行い、
実施はしていない。**

判断材料:
- 30人時点の実測で、送信(アップロード、全publisher分)が約6.5Mbpsだったのに対し、
  受信(ダウンロード、`lk load-test`集計)は約2.4Mbpsと、**アップロード側の需要の方が
  大きかった**
- prodのCPUは30人時点でも定常30%前後で余裕があり、パケットロスが受信者ごとに
  大きくばらついていた(0%〜47.3%)ことから、生成元側の**Wi-Fi固有の不安定さ**も
  疑われる
- モバイル回線(4G/5G)は基地局の帯域配分が下り優先で、一般に上りが下りより
  大幅に制限されやすく、家庭用固定回線と比べてもアップロードが改善するとは
  限らない。また無線という点は変わらず、モバイル特有の基地局共有・電波変動・
  キャリアQoS制御という別の不安定要因が加わる。CGNAT配下になりやすくTURN中継の
  挙動が変わる可能性もある(未検証領域)

**結論: 疑わしい原因(アップロード帯域不足・Wi-Fi不安定さ)のいずれに対しても
テザリングは改善ではなく悪化方向に働く可能性が高いため、切り替えは推奨しない。**
代替案として、一時的な別クラウドVPSの新規契約(東京リージョン、数時間・数百円
程度)を引き続き推奨する。

## 実測結果(2026-08-16実施、10〜30人ランプ)

「100人同時接続を想定した負荷テスト」の依頼を受け、本番grovina-livekit-prodに対して
`lk load-test`(v2.18.2)で段階的ランプテストを実施した。負荷生成元は暫定的に
作業端末(広島の家庭用ケーブル回線、Wi-Fi接続)を使用し、まず10〜30人規模で
生成元自体が先に限界を迎えないか確認する方針で実施した(①のRedis調査により
Redis自体の健全性は確認済みの前提)。

### 判断: 20〜30人付近で観測されたパケットロス増加は、prod側ではなく負荷生成元(この
作業端末)側の限界である可能性が高い

根拠:
- prodのCPUは30人時点でも定常時30%前後に収まっており、CPU逼迫の兆候がない
  (パケットロスがサーバー側の処理落ちによるものなら、通常CPU逼迫を伴う)
- 30人時点の全publisher・全subscriberは同一の1台(この作業端末)から生成しており、
  かつこの端末はWi-Fi接続の家庭用回線である。上り(publish)・下り(subscribe)の
  両方向のトラフィックを同時に1本の家庭回線・1本のWi-Fiで処理しており、
  ここが実際の律速要因になっている可能性が高い
- パケットロス率が受信者ごとに大きくばらついている(0%〜47.3%)。サーバー側の
  帯域逼迫であれば全受信者が比較的均等に影響を受けるはずだが、今回はごく一部の
  受信者だけ極端に悪化しており、Wi-Fi特有の間欠的な電波干渉・再送失敗
  (実際に`turnc ERROR: Fail to refresh permissions: all retransmissions failed`が
  2件記録された)に近いパターンである

### 今回はここで一旦停止

事前に合意した方針(「生成元がボトルネックになる兆候が出たら一旦立ち止まって相談する」)
に基づき、50〜100人規模への継続は行わず、ここで一旦停止した。10人までは
エラー・パケットロスともゼロで完全にクリーンな結果が得られている。100人規模まで
prod側の限界を正確に見極めるには、生成元を家庭回線から切り離す(帯域に余裕のある
別環境、例えば一時的なクラウドVPSからlk load-testを実行する)必要がある。

### 次のアクション(要判断)

- (A) 一時的な別クラウドVPSを新規に用意し、そこから50→75→100人規模のランプを
  改めて実施する
- (B) 今回の10人までのクリーンな結果と、20〜30人の(生成元起因の可能性が高い)
  参考値を踏まえていったん現状の負荷スコア重み・しきい値を維持し、100人規模の
  正確な検証は別途優先度を見て実施する

いずれも実施前に費用・所要時間を含めて改めて相談する。

## 重みの根拠となった想定帯域値(2026-08時点、コード調査ベース)

`components/AvatarSpace.tsx`の`startScreenShare()`は`setScreenShareEnabled(true)`を
オプション無しで呼んでおり、エンコード設定はLiveKit Client(`livekit-client`)の
デフォルト(`ScreenSharePresets.h1080fps15` + simulcast layer 1本)に従う。
これを元に、実際のライブラリ実装(`node_modules/livekit-client`)を読んで
導出した想定帯域は以下の通り(実測ではなくコードから導出した理論値である点に注意):

| 項目 | 想定帯域 | 根拠 |
| --- | --- | --- |
| 送信側(画面共有者、最大) | 約3.1Mbps | simulcast高レイヤー2.5Mbps(1920×1080/15fps) + 低レイヤー625kbps(960×540/15fps相当)の合算 |
| 受信側・サムネイル表示時 | 約625kbps | `adaptiveStream`により描画サイズが小さい間は低レイヤー(625kbps)のみ配信される |
| 受信側・全画面表示時 | 約2.5Mbps | 全画面化で描画サイズが拡大し、高レイヤー(2.5Mbps)に切り替わる |
| 参考: ビデオ通話1人あたり | 150kbps | 160×120/15fps固定・simulcast無効(既存設定) |

負荷スコアの`screen×20`は送信側3.1Mbpsをビデオ通話150kbpsと比較した比率
(約20倍)、`watching×17`はサムネイル〜全画面が混在する視聴を平均的に見た
比率から設定している。**これはコード上の理論値であり、実機での`lk load-test`
実測値と乖離している可能性がある**ため、下記の検証手順で必ず比較すること。

## ⚠️帯域上限についての重要な前提

Indigoの「1Gbps上限」は瞬間的なバースト上限であり、公式の「[安定運用の目安](https://web.arena.ne.jp/indigo/spec/guide.html)」
ページでは8GBプランのデータ転送量目安を**160GB/日**としている
(24時間平均で約14.8Mbps、業務時間帯8時間に集中しても約44Mbps相当)。
また「目安を超えるアクセスが続くとシステム保全のため利用を制限することがある」
と明記されている。

→ **今回の実測の主目的は「1Gbpsまで耐えられるか」ではなく、「実際に業務時間帯へ
負荷が集中したときに、この目安(14.8〜44Mbps)をどの程度の同時利用人数で
超えるか」を確認することである。** CPU上限より先に帯域目安に抵触する可能性が
高いため、CPU使用率だけでなくネットワーク送受信量(Mbps)を必ず記録すること。

## 追加タスク: TURN経由(relay)接続の強制検証(未実施)

- 確認後、`iceTransportPolicy`の一時的な変更は元に戻す

## 無制限プランによる想定シナリオの変化

スタンダード以上(スタンダード/プロ/ビジネス)は画面共有・ビデオ通話とも
1日あたりの時間上限が無くなったため、従来の「時間制限があるので短時間・
散発的な利用に収まりやすい」という前提が崩れる。特に以下を想定して
テストパターンを追加した:

- スタンダード以上のルームで、定員(15〜50人)の大半が終日ビデオ通話を
  つなぎっぱなしにするケース
- 同じルームで複数人が同時に画面共有を行い、それぞれに視聴者がつくケース
  (選択視聴モデルのため視聴者ごとに1本の画面共有ストリームが流れる)

## パターン1: ビデオ通話のみ

現行の低画質設定(160×120 / 150kbps / 15fps / simulcast無効)に合わせて実施する。

```
lk load-test \
  --url wss://livekit.yourdomain.com \
  --api-key <API_KEY> --api-secret <API_SECRET> \
  --room load-test-video \
  --video-publishers 10 --video-resolution low \
  --subscribers 10 \
  --duration 3m
```

`--video-publishers`を10 → 20 → 30 → 50と段階的に増やし、各回でノードの
CPU使用率・ネットワーク帯域(`docker stats`または`vmstat`/`sar`)を記録する。
ビジネスプラン(定員50人)が全員終日ビデオ通話する想定に対応するため、
50人時点での**実効帯域(Mbps)**が上記の目安(14.8〜44Mbps)に対してどの
位置にあるかを必ず確認する。

## パターン2: 画面共有のみ

画面共有は文字が読める必要があるため高画質のまま(圧縮しない)。`lk load-test`は
カメラ映像の負荷を模擬するツールのため、画面共有そのものの模擬は公式には
用意されていない。実務的には以下のいずれかで代替する:

- `--video-publishers`に加え`--video-resolution high`(1080p相当)を指定し、
  画面共有に近い高ビットレート配信を模擬する
- 可能であれば実際のブラウザ複数台で本物の画面共有を行い、同時視聴者数を
  変えながら実測する(`lk load-test`より手間はかかるが最も正確)

いずれの方法でも、1配信あたりの実測帯域を計測し、ビデオ通話1人あたりの
帯域との比率を出す。この実測比率が、上記「重みの根拠となった想定帯域値」
(送信側約3.1Mbps=約20倍、サムネイル受信約625kbps/全画面受信約2.5Mbps=
約17倍相当)から大きくずれていれば、
`app/master/MasterOnlineStats.tsx`の負荷スコア計算式(コメント含む)と
`deploy/livekit/monitor/check-load-score.mjs`の重み・THRESHOLDS、および
Tech Lead設計書の閾値(300/600/900/1200)を実測値に合わせて見直す。

**画面共有は無制限プランで時間上限が無くなったため**、1本あたりの帯域だけで
なく、「同一ルーム内で何本の画面共有が同時に成立しても目安帯域(14.8〜44Mbps)
を超えないか」を、本数を2本→5本→10本と増やしながら確認する。

## パターン3: 混合パターン(無制限プランの実利用を想定)

```
lk load-test \
  --url wss://livekit.yourdomain.com \
  --api-key <API_KEY> --api-secret <API_SECRET> \
  --room load-test-mixed \
  --video-publishers 30 --video-resolution low \
  --subscribers 30 \
  --duration 5m
```

上記のビデオ通話30人相当の負荷を土台にしつつ、パターン2の高負荷publisherを
数本(画面共有3〜5人相当)追加して、単一ノード(6vCPU/8GB)がどこで
CPU/帯域の天井に達するかを確認する。天井に達した時点の理論負荷スコア
(video×1 + screen×20 + watching×17)が、現在の「300超で2台目」という
しきい値と比べて余裕がある/ない場合は、しきい値を実測に合わせて調整する。

追加で、**スタンダード以上のプランを想定した「定員に近い人数が終日つなぎ
っぱなし」のワーストケース**(例: ビジネスプラン定員50人のうち40人がビデオ
通話、5人が画面共有中)を1パターン実施し、Indigoの帯域目安を1日あたりの
換算でどの程度消費するかを試算する(実測Mbps × 想定稼働時間で概算)。

## 記録する指標

各パターン・各段階で以下を記録する:

- CPU使用率(`docker stats livekit`)
- ネットワーク送受信量(帯域、Mbps。**Indigoの安定運用目安160GB/日との比較を
  必ず併記する**)
- メモリ使用量
- LiveKitのログに現れるパケットロス・再送の有無

- [ ] 画面共有・送信側の実測最大帯域を、想定値(約3.1Mbps)と比較し、
