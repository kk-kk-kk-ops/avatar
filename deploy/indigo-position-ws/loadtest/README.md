# 負荷試験ツール(2026-11追加)

`indigo-position-ws`のWSサーバーに対して疑似クライアントを量産し、7条件
(接続・移動パターン)での挙動を確認するためのツール。**本番トークン発行
API(`/api/indigo-token`)は経由せず、`SERVER_MODE=loadtest`専用インスタンス
に対してのみ接続する前提**(ルームIDは自動で`loadtest-`接頭辞を付ける)。

## 事前準備: loadtest専用インスタンスの起動

本番とは別ポート・別鍵で起動する(本番トークンは一切受け付けない)。

```bash
cd deploy/indigo-position-ws
SERVER_MODE=loadtest \
INDIGO_WS_TEST_SECRET=<試験専用の適当な秘密鍵> \
INDIGO_WS_TEST_KID=loadtest \
WS_PORT=8789 \
ADMIN_PORT=8790 \
node server.mjs
```

## 基本的な使い方

```bash
node loadtest/run.mjs \
  --ws-url ws://<ホスト>:8789 \
  --secret <上と同じINDIGO_WS_TEST_SECRET> \
  --rooms 1 \
  --clients-per-room 50 \
  --hz 5 \
  --duration 150 \
  --moving-ratio 1
```

## オプション一覧

| オプション | 既定値 | 説明 |
|---|---|---|
| `--ws-url` | (必須) | 試験対象のWSサーバーのURL |
| `--secret` | (必須) | `INDIGO_WS_TEST_SECRET`と同じ値 |
| `--kid` | `loadtest` | `INDIGO_WS_TEST_KID`と一致させること |
| `--rooms` | `1` | ルーム数(例: 50人×3部屋なら`--rooms 3 --clients-per-room 50`) |
| `--clients-per-room` | `50` | 1部屋あたりの人数 |
| `--hz` | `5` | 1クライアントあたりの送信頻度(回/秒) |
| `--duration` | `150` | 試験の継続時間(秒) |
| `--moving-ratio` | `1` | 継続的に移動するクライアントの割合(0〜1)。条件2(全員移動)は`1`、条件3(一部のみ)は`0.2`等、条件4(全員停止)は`0` |
| `--churn-interval-s` | `0` | この秒数おきに一部のクライアントを強制切断する(条件5・6用)。`0`で無効 |
| `--churn-fraction` | `0` | 強制切断する割合(0〜1) |
| `--map-w` / `--map-h` | `2000` | マップサイズ(試験対象のトークンに埋め込む値) |

## 7条件との対応

| # | 条件 | 実行方法 |
|---|---|---|
| 1 | 全員同時接続 | 既定(全クライアントがほぼ同時に`start()`される) |
| 2 | 全員同時移動 | `--moving-ratio 1` |
| 3 | 一部のみ移動 | `--moving-ratio 0.2`等 |
| 4 | 全員停止 | `--moving-ratio 0`(3秒おきのハートビートのみ) |
| 5 | 同時入退室 | `--churn-interval-s <duration> --churn-fraction 1`(試験時間内に1回、全員強制切断) |
| 6 | 切断と再接続 | `--churn-interval-s 30 --churn-fraction 0.2`等、継続的に一部を切断 |
| 7 | サーバー再起動 | ツール自体はこの条件専用のオプションを持たない。`--moving-ratio 1`等で実行中に、**別のターミナルから試験対象サーバーのプロセスを再起動し**、再接続の様子を観察する |

## 出力される指標

- 接続試行数・接続成功数
- 4005(不正メッセージ連打)切断件数(0件であるべき。1件でもあれば調査対象)
- 配信遅延(受信時刻 - 送信側が埋め込んだ`t`)のp50/p95/p99(ミリ秒)。**複数の生成元マシンを使う場合、各マシンの時計がNTP等で同期されていないと、この数値の正確性が損なわれる点に注意。**
- 配信遅延は全件ではなくリザーバーサンプリング(最大20万件)による近似値
- **配信成功率**(2026-11追加): 各クライアントについて「同じルームの他クライアントが実際に送信した件数の合計(=本来届くはずだった件数)」と「自分が実際に受信した件数」を比較し、全体の割合を算出する。100%未満であれば取りこぼしが発生している
- **試験側(生成元)マシンのCPU使用率・受信帯域**(2026-11追加): 10秒ごとにサンプリングし、平均・ピークを最後に表示する。外部コマンド(vnstat/sar等)への依存を避けるため、Node標準の`os.cpus()`とアプリ内で集計した受信バイト数から算出している。**この値が高止まりしている場合、計測結果(配信遅延・配信成功率)がサーバー側ではなく試験側の限界を反映している可能性がある**(複数台構成での負荷分散を検討すること)

サーバー側の`[metrics]`ログ(受信/配信件数のピーク、送信間引き件数、move拒否
理由別件数)とあわせて見ることで、クライアント側(本ツール)・サーバー側
双方の視点から状況を確認できる。

## immediate/tick中継方式の比較

試験対象サーバーの`RELAY_MODE`(`config.mjs`、環境変数`RELAY_MODE`)を
`immediate`/`tick`で切り替え、同じ条件・人数で2回実行して本ツールの
出力(配信遅延)とサーバー側の`[metrics]`(帯域相当の件数)を比較する。
